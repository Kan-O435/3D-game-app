## Original-game reference (CloverPit) — researched 2026-09-19

Read from the public fan wiki (cloverpit.wiki.gg) and guides via web fetch — summaries, so treat exact numbers as approximate and re-check a page before relying on one. Sources: wiki.gg `Deadlines`, `Patterns`, `Symbols_Board`, `Slot_Machine`, `Clover_Tickets`; gametruth beginner guide; Wikipedia. (The Steam "Mechanics Explained" guide rate-limited us.) Kept here so the parity work doesn't have to be rediscovered.

- **Structure**: a *deadline* = **3 rounds**. Each round you pull the lever and pick **"Most Spins" (7 spins)** or **"Fewer Spins" (3 spins)** if you can afford the lever; broke = one free pull. Lever cost is in coins and rises each deadline ("starting at 7 coins for 7 spins").
- **Debt** (fixed every run, exponential): deadline 1 = **75**, 2 = **200**, 3 = **666**, 4 = **2,222**, 5 = **12,500**, 6–10 up to ~6,000,000, later absurd. Hard mode +25% cumulative. Not paying by the end of the deadline = death ("trapdoor").
- **Paying**: coins go into an **ATM at any time** (not only at the deadline); deposits earn **interest starting at 7%** (compounding across deadlines; charms raise it). Finishing early gives a **deadline bonus of 6 × (deadline number) coins** and **+4 clover tickets per skipped round**.
- **Two currencies**: **coins** (debt, lever) and **clover tickets** (shop). Tickets come from choosing Fewer Spins, skipping rounds, ticket-modifier symbols, phone calls, selling charms. Tickets buy **Lucky Charms** (150–160 of them) and reroll the shop / phone calls.
- **Symbols**: 7 — lemon, cherry (2 coins, ~19.4%), clover, bell (3, ~14.9%), diamond, treasure (5, ~11.9%), seven (7, ~7.5%). **Modifiers** on symbols: Golden, Token, Ticket, Repetition, Battery, Chain (+DLC ones).
- **Payout formula**: `symbol value × symbols multiplier × pattern value × patterns multiplier` — multiplicative, which is how the exponential debt gets paid.
- **Patterns** (base value): HOR ×1, VER ×1, DIAG ×1, HOR-L ×2, HOR-XL ×3, ZIG ×4, ZAG ×4, ABOVE ×7, BELOW ×7, EYE ×8, JACKPOT ×10 (whole screen one symbol); Angel's Hand unlocks small ones (HOR-S/VER-S/DIAG-S ×0.5). **A larger pattern that contains a smaller one blocks it** (except Jackpot). Board size wasn't stated on the pages read.
- **Meta**: memory cards (starting perks), phone calls (sacred/dark offers → different endings), several endings, endless mode.

### How this project differs today (as of the pay-at-deadline change)
Linear tiny debt (12, 20, 28…) vs exponential; 15 free turns per stage vs 3 rounds × (3|7) spins with a coin lever cost; automatic payment on the last turn vs ATM + interest + early-finish bonus; one currency vs two (coins/tickets); ~12 additive charms vs 150+ (many multiplicative); 15 symbols + wild/scatter vs 7 symbols with modifiers; additive `match-length × symbol` payout vs the 4-factor multiplicative formula; row-based patterns (+V/diagonals via charms) vs the named-pattern set with containment blocking; no phone/endings/endless.

## Decisions

Notable choices made along the way that aren't obvious from the code and would be easy to accidentally reverse or contradict later. One line: what + why. (Big architectural ones already live in `CLAUDE.md` — don't duplicate those here; this is for the smaller in-the-weeds ones that come up while implementing.)

- **Paylines are matched left-to-right from column 0 along a pattern** (`src/game/paylines.ts`): still the classic rule, now generalized from rows-only to a `PATTERNS` list (see the pattern-charm decision below).
- **`SpinButton` (`src/ui/`) was built early, in Phase 5 instead of its scheduled Phase 8**: the reel animation needed something to trigger a spin to be testable at all. It's a real (if minimal) start of the HUD, not a throwaway — Phase 8 extends it rather than replacing it.
- **The store decides the spin result immediately; the reel animation only delays revealing it** (`src/store/gameStore.ts` + `src/scene/ReelGrid.tsx`): `spin()` computes the final grid/wins up front, and `ReelGrid`'s roll-then-stop animation is purely visual, calling `finishSpin()` when it catches up. Keeps game logic and animation timing fully decoupled.
- **No sound files — all audio is synthesized** (`src/audio/audioEngine.ts`): oscillators + gain envelopes for SE, two detuned drone oscillators for BGM. Same "prove the plumbing, not the content" approach as the placeholder icon textures. Swap in real audio assets later without changing the call sites (`initAudio`/`playSpinStart`/`playReelStop`/`playWin`/`setMuted`).
- **Paylines now match from 2 symbols, not 3** (`src/game/paylines.ts`, `MIN_MATCH = 2`): with 15 weighted symbols a 3-run hit only ~3% of spins (EV ≈ 0.09 coin/spin), which made any turn-limited quota pure luck. 2-runs hit ~29% of spins. Multipliers were retuned to `{2:2, 3:6, 4:20, 5:60}` alongside. Supersedes the earlier "3-match" rule.
- **[superseded by the pay-at-deadline decision below] Money carries over between stages; quota was a target on the running total** (`src/store/gameStore.ts`, `src/game/stage.ts`): surplus from a stage isn't wasted, quota therefore grows cumulatively (10, 23, 39, 58, 80…). Turns reset to 15 each stage.
- **Turn is spent at `spin()`, payout is banked at `finishSpin()`** (`gameStore.ts`): money only changes when the reels visibly stop, so the HUD number can't spoil the result. Clearing the quota on the very last turn counts as a clear, not game over. `playWarning()` fires when ≤2 turns remain after a spin that neither cleared nor ended the run.
- **HUD callouts are CSS-animated and keyed, not timer-driven** (`src/ui/Hud.tsx` + `index.css`): the "+N" pop and "STAGE n CLEAR" banner replay by changing the element's `key`, and fade out via `animation-fill-mode: forwards` — no `setTimeout`/effect state. The payout pop is gated on `!isSpinning` so it appears in step with `money` updating, not before the reels stop.
- **RETRY lives on `GameOverScreen`, not `SpinButton`**: `SpinButton` is just PUSH and hides itself on game over, so there's one obvious action on that screen.
- **Charms are once-each, bought with money, and money is also the pool the debt is paid from** (`src/game/charms.ts`, `gameStore.ts`): spending coins in the shop makes the next (cumulative) quota harder — that's the intended dilemma, not a bug. Simulation (real spin/payout code, 4000 runs): never buying → median stage 4, reach stage 10 ≈ 1–2%; buying everything affordable → median 2 but reach stage 10 ≈ 15%. So buying is a real gamble (worse early, far better if it snowballs). Not playtested — retune prices/effects if it feels wrong.
- **Charm prices were set to ≈2× a charm's expected gain per stage** (`charms.ts`): measured per charm at 15 turns/stage. `pity-coin` (+1 on a miss) is by far the strongest (~+11/stage) so it costs 22; `candle-stub` (+1 turn) is weak in raw coins so it's cheap (6). Re-measure if the payout table or quota curve changes.
- **Turns reset in `leaveShop()`, not at stage clear** (`gameStore.ts`): so a +turn charm bought in the shop applies to the stage about to start. Stage-clear bonus coins (`fate-dice`) are added at clear time, before the shop.
- **Deploy moved to the very last phase** (`CLAUDE.md` roadmap): decided to finish the game (charms, patterns, atmosphere, polish) before wiring Cloudflare, so Phase 9 "Deploy" became Phase 14.
- **Extra win patterns are unlocked by charms, not always on** (`paylines.ts` `BASE_PATTERN_IDS`, `charms.ts` `v-scar` / `crooked-blade`): turning all 7 patterns on from the start would have ~2.3x'd the payout and invalidated the quota/charm tuning. Gating them behind shop charms keeps the baseline balance intact and makes patterns a real purchase choice. Extra patterns pay at `payoutFactor` 0.6 per line (fractional per-line payouts are fine — `computePayout` rounds the spin total); each pattern charm adds ~+11 coins/stage, same tier as `pity-coin`, hence price 22. If the game should feel richer from turn one, the alternative is to make them always-on and rescale quota + charm numbers.
- **Wild/scatter re-tuned the whole payout table** (`symbols.ts`, `paylines.ts`): adding a wild (weight 2) and scatter (weight 9) in place of the two old "super rare" symbols raised base EV from ~1.83 to ~2.66 per spin, so match multipliers were cut to `{2:1.5, 3:4.5, 4:15, 5:45}` to land at ~2.00 (line ≈ 1.65 + scatter ≈ 0.36; scatter fires about once per 25 spins). That's ~9% richer than before the change — stage-1 clear is now ~92%, no-buy median still stage 4. Charm prices were re-measured at ≈2× gain (see `charms.ts`); re-measure again after any symbol/payout change.
- **Charms that boost "rare" symbols must not include the specials** (`charms.ts`): `black-cat-eye` first boosted ids 10–14 ×4, which silently made wild/scatter far more common (EV/spin jumped to ~9.7). It now boosts only 10–12; wild/scatter have their own charms. Same trap applies to any future range-based boost.
- **A scatter count is not a "long run"** (`computePayout`): `skull-ring` (4+ match ×2.5) skips scatter wins, otherwise 4+ scatters would get an unintended multiplier. `silver-tooth` (+1 per winning line) does count a scatter win as a line.
- **[since checked in screenshots — see "Looking at the game"] Atmosphere was written blind** (`src/scene/Lighting.tsx`, `FixedCamera.tsx`, `Atmosphere.tsx`): the dev environment has no browser/WebGL, so only types, build, the pure mood/heartbeat logic and dev-server module transforms were checked. First real look should check: (a) overall brightness — enabling `EffectComposer` changes how tone mapping is applied, so `<ToneMapping ACES_FILMIC>` was added to approximate the old look; (b) the vignette/noise/fringe strengths at mood 0 vs 1; (c) whether the flicker/brownout is too frequent; (d) camera tremble/kick amount. All the knobs are plain numbers at the top of each effect.
- **Mood = low-turn tension + slow stage dread, shared through one mutable object** (`src/game/mood.ts`, `src/scene/moodState.ts`): `tensionFor` is 0 until `WARNING_TURNS` remain, then 1/3 → 2/3 → 1 (peak on the final turn, including while its reels spin); `dreadFor` adds up to 0.3 by stage so deeper stages are darker even with turns to spare; game over pins mood at 1. It's a mutable module object, not React state, so per-frame readers (lights/camera) don't re-render; only the post-processing props follow it in 0.02 steps. The heartbeat uses tension alone — dread never triggers it.
- **Debt is paid at the deadline, not "reach a quota early"** (`gameStore.ts` `finishSpin`, `stage.ts` `dueForStage`) — user's call, to match the original's pressure: on a stage's last turn `due` is deducted from money; short = game over, enough = pay, leftover carries, shop opens. Having the money early does nothing (no early exit), so a stage always uses all its turns. The deadline turn's own payout counts toward the payment, and the payment is checked only after the reels stop. `fate-dice` (+6) pays *after* the debt is taken.
- **The pay-at-deadline switch made the game much easier at first and was retuned** (`stage.ts`): reusing the old per-stage increments (`10+3(s-1)`) let a no-charm run reach stage ~13 — the old early-exit rule had quietly capped income. Simulation (real spin/payout code, 4000 runs) picked `due = 12 + 8(s-1)` (12, 20, 28, 36…): no charms → median stage 4, ~1% reach 10; buying wisely (keep a cushion for the next payment) → median 4 but ~13–17% reach 10; buying everything affordable → median 3, ~26% reach 10. Stage-1 pass ≈ 92%. Not playtested.
- **Store field/UI naming: `quota` → `due`**: HUD says DUE / DEADLINE, shop says PAID / NEXT DUE, game over says "Couldn't pay". The original's exact terms aren't confirmed — rename if the user prefers "debt"/"ノルマ".
- **Scope decision: follow the reference site's feature level, drop full-CloverPit parity** (user, after seeing it would be heavy): no 3-round deadlines, ATM/interest, tickets or exponential debt. The CloverPit research above stays as background only. The earlier "pay-at-deadline" rule *is* kept — it matches the reference (納付 at the end of the turns).
- **All money numbers are ×5** (`symbols.ts` payouts 10/20/40/100, `SCATTER_PAYOUT` 30/100/300, flat charm bonuses ×5, prices, `stage.ts`): once every spin costs a fee (2+), the old scale (EV ≈ 2 coins per spin) left the fee eating half the income and made every curve near-unwinnable. At ×5 a spin is worth ≈10 coins, so a 2–5 coin fee is a modest tax. Charm prices re-measured at ≈2× gain per stage at 12 turns.
- **Performance points (P) are a second, softer constraint** (`symbols.ts` `perf`, `paylines.ts`, `stage.ts`): commons/uncommons perf 2, rares 1 (rare = big coins, little P — the reference's "smart models are slow" tension, loosely), wild 2, scatter 0. A win earns `perf × (matched − 1)`; a spin averages ~0.7 P. Requirement is 3 at stage 1 growing by 1 every 2 stages; the slope was kept low because at +1/stage most failures were P failures (unfair while rich). `overclock` (×1.5 P) is the charm answer to it. Retune freely — `perfNeeded` 0 turns the mechanic off.
- **Terms** (`stage.ts`): 12 turns/stage, start 30 coins, fee `2 + ⌊(s−1)/3⌋`, due `28 + 14n + 4n²` (n = stage−1; 28, 46, 72, 106…), perf needed `3 + ⌊n/2⌋`, reroll 10, 8 shop slots. Simulated (real code incl. rate limits, 3000 runs): never buying → median stage 4, stage-1 pass ≈ 89%, ~0% reach 10; buying wisely (keep a cushion for the next due) → median 4, ~13% reach stage 10; buy-everything autoplay → mean 3.8 stages, deepest ~19. The quadratic term in `due` is what keeps a snowballing charm build from running away (with linear dues the top 10% hit stage 30). Re-tuned once after the rate-limit symbol cut income ~9% (first tune was 32/52/80/116, start 20, perf 4). Not playtested.
- **You can't spend below the coming spin fee in the shop, and a stage entered with less than the fee goes straight to its deadline** (`canSpend`, `acceptOrder` in `gameStore.ts`): found by autoplay — buying everything left 1 coin against a 2-coin fee, i.e. a stage you couldn't even start. Also, being unable to pay the fee mid-stage forfeits the remaining turns and settles the deadline immediately (the original gives a free pull when broke; we chose the harsher, simpler rule).
- **Camera stations by `status`** (`FixedCamera.tsx`): briefing → left wall, shop → right-hand counter, everything else → the machine; readable content is DOM overlaid with a delayed `.fade-in`, the 3D props (`Props.tsx`) are only enough to make the move look like somewhere. Not seen rendering yet — the station poses/light positions are the first things to check.
- **RETRY skips the title screen** (`restart()` → `briefing`): the title/PUSH screen is only for the first load.
- **The `6` rate limit is a `curse`-kind symbol that takes id 12** (`symbols.ts`, `paylines.ts` `findRateLimit`, store `spin`): keeps the total at 15 by replacing the third rare symbol (rares are now ids 10–11). Weight 8 → three or more anywhere on the grid about once per 37 spins (≈2.7%). It never joins a run and wild doesn't bridge it. When it hits, the store replaces the wins with a single `rate-limit` marker (payout 0, cells = the curses) so nothing is paid or highlighted as a win; `computePayout` also returns 0 for it so bonuses/consolation can't leak through. The fee is still paid. The reel cells tint red and there's a buzz + a "RATE LIMIT" callout. The `firewall` charm (price 20 — worth only ~3 coins/stage in expectation, it mostly removes variance) turns it off. Interprets the poster's "6が3つ" as "3 anywhere" (like the scatter), not "3 in a row" — unconfirmed.
- **Rate limit cost ~9% of income, so `black-cat-eye` now boosts ids 10–11 only** (it used to include 12, which would have boosted the curse ×6): same trap as the wild/scatter one — any range-based boost must skip specials.
- **Symbol values drift per stage, and only ordinary symbols do** (`src/game/drift.ts`, store `finishSpin`/`leaveShop`): the poster says values "change now and then" but not how, so this is a guess — a 12% chance after each spin that isn't the deadline turn, one random *normal* symbol (never wild/scatter/curse) gets a new factor from {0.5, 0.75, 1.5, 2} (always different from its current one), and everything resets when the next stage starts. That's ~1.3 changes per 12-turn stage and no long random walk. Measured effect on the average spin: about +1% (9.37 → 9.46 coins), so no retune was needed. The change applies from the *next* spin — never to a result already decided. The payout table splits a tier into separate rows when only some of its symbols drifted, marks them ▲/▼ with ×factor, and the HUD shows a short "相場変動" callout. Retune `DRIFT_CHANCE`/`DRIFT_FACTORS` freely; nothing else depends on them.
- **Tests are vitest, colocated as `*.test.ts`, and cover logic only** (`npm test`): the scratch scripts used to verify every earlier phase were ported into `src/game/*.test.ts` (patterns, wild/scatter/curse, performance, payout table, charms, terms, mood, drift), `src/store/gameStore.test.ts` (screen flow, spin/fee, deadline, shop, rate limit, drift, autoplayed full runs) and `src/audio/audioEngine.test.ts` (heartbeat). Store test: `vi.mock` the audio module, `setState(getInitialState(), true)` between tests, and force the RNG with `vi.spyOn(Math, 'random')` (`forceSymbol` picks a symbol's weight bucket — tied to the weight order in `symbols.ts`). Mutation-checked: breaking the due curve, the rate-limit zeroing, or the performance check each fails a test. **Not covered**: React/three rendering, the camera, the HUD/shop DOM — those were checked ad hoc in jsdom (not kept) and by eye. The balance *simulations* (median stage, price-vs-gain) are still throwaway scripts, not tests.
- **[partly superseded: the coins/performance LED windows, turn lamps and DOM marquee were removed when the numbers moved onto the 3D machine; the panels, buttons, payout placard and win banners remain] DOM UI restyled as a slot cabinet — written blind** (`src/index.css` "Slot-cabinet look", `src/ui/*`): gold-trimmed dark-red panels, black LED windows with glowing amber/green/blue digits over unlit "8"s (`LedNumber`, rolls to new values over 600 ms), a segmented progress bar, **one round lamp per turn left** (the last `WARNING_TURNS` go red and blink), a chasing-bulb marquee with the stage number (bulbs speed up while spinning, flash on a win, go red on a rate limit — driven by `data-state`), glossy arcade buttons (`.arcade-btn`, variants `.gold`/`.gray`/`.small`, the title PUSH pulses), a brass PAYOUT placard with amber numbers, and result banners tiered by size (`winTier`: WIN < 100 ≤ BIG WIN < 500 ≤ JACKPOT with a screen flash). Colours are CSS variables on `:root`. Uses `color-mix()` and `steps(n, jump-none)` (modern browsers only). First things to look at: whether the top-left panel + marquee + banner overlap on a small window, the LED glow strength, and the banner positions (`top: 26%`, drift 11%). **Not touched**: the 3D cabinet itself (still a plain box with the reel grid) — a marquee sign, lever and button plate on the model would be the next step for the "slot" feel; the order sheet keeps its paper look on purpose.
- **Default screen rebuilt after the reference's title screenshot** (`src/scene/Cabinet.tsx` & co., `Room.tsx`, `Props.tsx`, `App.tsx`): the machine is proper geometry now (plinth + red body + sign box + framed reel window + plates + PUSH panel + lever) with everything textual drawn into small canvas textures (`MachineScreens.tsx`) and sampled nearest-neighbour; the room is a 6.8×3.2×6 m cell with a barred window behind the machine on the right (blue additive glow on wall + floor and a blue spotlight), a bucket, crates, pipes, the order wall on the left and the counter on the right; the camera sits ~3.5 m back at (0, 1.3) looking straight at the machine so it is centred on screen (it was briefly offset to sit left of centre like the reference; the user asked for it centred). Placeholder icons are dark tiles with a simple coloured glyph (`icons.ts`) — the reference's AI-logo look, without copying anything.
